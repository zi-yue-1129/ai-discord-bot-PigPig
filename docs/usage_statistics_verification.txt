Root causes established in the baseline code

1. Command recording had storage but no producer.
   dashboard/services/stats_collector.py:122 defined record_command, but no bot
   or cog called it. StatsCog had only a message listener and log migration.
   Prefix and application command invocation events were never connected to
   command_events. New listeners record attempts before command completion,
   including errors, DMs (guild_id "0"), qualified subcommand names, and hybrid
   slash commands once. Autocomplete and component events are excluded.

2. LLM recording was attached to successful agent workflows, not model calls.
   llm/orchestrator.py:559-577 and :741-763 recorded after successful awaits,
   always with success=True. Its error/fallback branches did not record failures.
   Durations included agent/tool/Discord work, rather than the model lifecycle.
   llm/utils/model_init.py:13-34 returned bare models without statistics hooks.
   Consequently other consumers of that helper had no recording at all.
   cogs/memory/services/event_summarization_service.py:583 also returned a bare
   init_chat_model result for raw fallback, bypassing the shared helper.
   llm/model_manager.py:111 passed fallback model strings to LangChain middleware;
   inspection of the installed middleware confirmed it calls init_chat_model
   directly for those strings. An offline real-agent test demonstrated the
   missing fallback row before its fix.
   scripts/reconstruct_stats.py:127 hardcodes historical LLM events as duration=0,
   success=1. This is additional code evidence for success-only historical rows;
   this script was not run or modified.

   The shared helper now attaches model lifecycle callbacks, recording one event
   per run ID, preserving original provider-qualified names (including vllm),
   capturing wall-clock start timestamps and monotonic elapsed durations, and
   recording failures and timeout cancellation. Existing callbacks survive.
   Missing collectors and recording errors are logged at error level (with a
   traceback for storage failures) and never interrupt the model call; a failed
   provider call still surfaces its own error. (Revised after review: the first
   version raised, which let a locked database fail user-facing replies.) Memory raw
   fallback and configured middleware fallback models use this same helper.
   Guild context is forwarded throughout helper consumers. Old orchestrator
   aggregate writes were removed to avoid double counting.

Limits

The bot was not connected to Discord or to real providers. Production data and
logs were not inspected, so the exact cause/timing of the September/October
monthly count collapse and the origin of existing success-only rows cannot be
attributed conclusively. The code-level missing recording paths are reproduced
and repaired. Provider-internal HTTP retries remain one LangChain invocation;
separate agent rounds and fallback invocations each receive their own event.
Downstream parser errors after a successful provider response do not relabel that
provider invocation as a failure. Process termination cannot guarantee a terminal
row because recordings are emitted at model end/error. The entire legacy suite
cannot be claimed green; all 21 baseline failures/errors remain as documented.
